# lhg-mp-audit：食谱自检流程

> 目标：交付前，把"吃出问题"的可能性降到最低。
> 核心纪律：**先跑脚本（机器），再做评审（人）；blocker 不清零，不许说做完了。**

> **免责声明**：本 skill 输出不是医疗建议。慢病/备孕人群请遵医嘱。

## 1. 何时使用

- 一周食谱编完、交付前 → 跑全流程
- 只想快速看一眼 → 只跑第 2 步（脚本），5 秒出结果
- 用户反馈"按食谱吃不舒服" → 用第 5 节清单复盘，定位是热量/过敏原/执行哪环的问题

## 2. 第一步：跑确定性审计脚本（必做，零 AI 成本）

在交付目录执行插件自带的审计脚本：

```
python3 <插件目录>/scripts/audit/meal_audit.py --target <交付目录>
```

交付目录里应有：`menu*.md`（一周食谱，每餐带 `P:xxg C:xxg F:xxg` 宏量标注）、`shopping*.md`（采购清单）、`meta.json`（人群/目标区间/过敏原/来源）。

- 脚本输出 JSON（含每条发现的文件、行号、规则说明）与人类可读报告，共 31 条规则。
- 有 blocker 时脚本以非零 exit code 退出——这是设计，不是 bug。
- `--fail-on` 控制 exit code 语义：默认 `blocker`；想要更严的门禁可设为 `warning`。
- 脚本只做"机器可判定"的事：营养素偏差、过敏原、禁忌食材、重复菜品、清单对应、免责声明。它判定不了"好不好吃"，那是第 5 步的事。

### 2.5 meta.json 规范

```json
{
  "group": "减脂",
  "targets": {"kcal": [1500, 1800], "protein_g": [90, 120],
              "carbs_g": [150, 200], "fat_g": [40, 60]},
  "allergies": ["花生"],
  "source": "《中国居民膳食指南（2022）》"
}
```

- `group`：减脂/增肌/备孕/慢病四选一，决定禁忌规则（缺失 → DSC-002 blocker）
- `targets`：每日目标区间，NUT-* 规则的判定基准（缺失 → SRC-002，规则跳过）
- `allergies`：过敏原清单，ALG-001 用
- `source`：口径来源（缺失 → SRC-001 warning）
- 字段缺失会导致对应规则跳过（不是"通过"，是"没查"——两回事）

规则覆盖八类：
| 类别 | 规则数 | 查什么 |
|---|---|---|
| 营养素 NUT-* | 8 | 当日热量/蛋白/碳水/脂肪 vs 目标区间上、下限 |
| 过敏原 ALG-* | 1 | 申报过敏原全周零出现 |
| 人群禁忌 TAB-* | 7 | 备孕（生食/酒精/高汞鱼）、慢病（高盐/高糖）、减脂（油炸/含糖饮料） |
| 多样性 DIV-* | 4 | 连续重复、周重复≥4、蛋白来源<3、蔬菜<5 |
| 采购清单 SHP-* | 5 | 缺清单、项数过少、重复项、无分类、食材未进清单 |
| 免责声明 DSC-* | 2 | 食谱缺"非医疗建议"声明、meta 缺人群 |
| 来源 SRC-* | 2 | 未注明膳食指南来源、目标区间缺失 |
| 份量 POR-* | 2 | 某餐缺宏量标注、某天不足三餐 |

## 3. 第二步：分级

| 级别 | 定义 | 处理 |
|---|---|---|
| blocker | 吃出问题的风险：过敏原命中、备孕/慢病禁忌、热量/蛋白低于下限、缺免责声明、缺采购清单 | 必须修，不修不许交付 |
| warning | 大概率翻车：营养素超上限、菜品重复、清单项过少 | 本次修掉；修不掉写理由进报告 |
| nit | 洁癖项：清单重复项 | 顺手修 |

分级是死的，判断是活的：如果某条 warning 在这个人群里就是高风险（如备孕人群的"减脂忌油炸"不适用，但"酒精"必须零容忍），按人群调整分级，并在报告里写清理由。

## 4. 第三步：修复 blocker

1. blocker 逐条修，修一条跑一遍脚本确认消失。
2. 修复顺序：**过敏原/禁忌先修**（这些是"正在流血"的）→ **营养素下限**（热量/蛋白不够）→ **免责声明与清单**。
3. 修不掉的 blocker：列进报告的"需人工处理"区，**不许**为了清零而删规则或改脚本阈值。
4. 禁忌食材靠"替换"修：把生鱼片换成清蒸鱼、把奶茶换成无糖豆浆，不许靠删规则修。

## 5. 第四步：人工评审（脚本覆盖不到的）

### 可执行性清单
- [ ] 食材买得到吗？（菜市场/生鲜 app 能买到全部食材吗）
- [ ] 做法会吗？（"清蒸三文鱼"对不会做饭的人就是天书，要配做法说明或替换）
- [ ] 时间够吗？（每餐备餐时间是否在用户接受范围内）
- [ ] 预算超了吗？（按当地物价估算一周采购总价，对照画像卡预算）

### 可持续性清单
- [ ] 连续吃 7 天会腻吗？（口味/烹饪方式是否轮换）
- [ ] 有"快乐餐位"吗？（完全无快乐的食谱，弃餐率极高）
- [ ] 外食场景有替换方案吗？（至少工作日午餐给一个食堂/外卖替换）

### 人群专项清单
- [ ] 备孕：是否再次确认无生食/酒精/高汞鱼？（Ctrl+F 全文搜一遍）
- [ ] 慢病：盐/糖/油的控制是否有具体落点（如"酱油每天不超过 X 勺"）？
- [ ] 减脂：热量缺口是否在 300~500kcal？（缺口过大不可持续）

### 评审输出
每项写"通过 / 不通过（原因）"，不通过的进待办，不许写"大概没问题"。

## 6. 第五步：输出报告

报告模板：

```markdown
# 自查报告：<人群>-<周期>（日期）
## 结论：通过 / 不通过
## blocker（n）：已修 n，剩余 n
- [规则ID] 文件:行 —— 说明 —— 状态（已修/需人工）
## warning（n）：已修 n，豁免 n（理由）
## nit（n）
## 人工评审：可执行性 x/y，可持续性 x/y，人群专项 x/y
## 需人工处理
- ...
```

报告建议存进交付目录（如 `audit-YYYYMMDD.md`），下次调食谱时对照。

## 7. 豁免规则

- 豁免只针对 warning/nit，blocker 不许豁免（过敏原、禁忌、免责声明必须处理）。
- 豁免必须写理由 + 有效期（如"周四晚餐外食场景，已给替换方案"），到期复查。
- 豁免清单进报告，藏着不写等于没豁免。

## 8. 反模式

- ❌ 只跑脚本不做人工评审——脚本抓不到"这菜他根本不会做"这种问题
- ❌ 为了清零改脚本规则——这是作弊，不是自查
- ❌ 禁忌食材靠删规则"修掉"——吃出问题的是用户，不是脚本
- ❌ "先发了再说，不舒服再改"——过敏原和禁忌没有"再改"的机会
- ❌ 自查报告只写"通过"两个字——没有过程的结论不可信
- ❌ 给慢病食谱承诺疗效——"按这个吃能降糖"越界了，红线

## 9. 误报处理

规则是启发式，一定会误伤。误报不可怕，乱处理才可怕：

1. **判断三问**：这道菜真的有问题吗？这条规则的本意是什么？按规则改了会不会破坏营养均衡？
2. **确认误报**：记入报告的豁免清单并写清原因（如"'花生'指花生油且用户仅对花生果仁过敏，已与用户确认 —— 豁免 ALG-001"）。
3. **拿不准**：按 warning 处理，不要直接忽略。
4. **规则本身有问题**：附最小复现食谱提 issue（见第 10 节），不要自己改脚本阈值。

## 10. 自检与反馈

每次执行完本 skill，做一次轻量自检：

1. 脚本是否真的跑了（而不是"我看了一遍觉得没问题"）？→ 没跑不算做。
2. blocker 是否清零或全部列入"需人工处理"？→ 有遗漏就补。
3. 人工评审清单是否逐项打勾？→ 打勾要有依据（第几天哪一餐）。

标准冒烟用例：对插件自带的 `fixtures/` 跑脚本，确认坏 fixture 的 blocker 全命中、好 fixture 零 blocker（见仓库根 `smoke_test.py`）。

反馈渠道：以 `[QC] <一句话问题>` 为标题提交到 https://github.com/lhg-plugs/lhg-meal-plan/issues，正文写清"输入 → 错误输出 → 期望输出"。规则误报/漏报请附最小复现食谱。
